# Карта мест (POI) — вариант 8

Лабораторные работы по Java. Все лабораторные — один проект, каждая следующая добавляется поверх предыдущей.

## Как запустить

Нужна Java 21 или новее.

```
./gradlew run          # Linux / macOS
gradlew.bat run        # Windows
```

## ЛР 1. Модель данных

| Файл | Что в нём |
| --- | --- |
| `Category.java` | перечисление категорий мест |
| `Place.java` | базовое место: id, название, категория, широта, долгота |
| `ModeratedPlace.java` | место «на модерации», только чтение |
| `Editable.java` | маркерный интерфейс «можно изменять» |
| `NetworkPlace.java` | сетевое место: можно изменять, есть сайт и телефон |
| `ErrorCode.java`, `CsvException.java` | своё исключение с кодом ошибки |
| `CsvFile.java` | чтение и запись CSV, битые строки пропускаются |
| `MainFrame.java` | окно: таблица, кнопки, диалоги |
| `Main.java` | точка входа |

Формат CSV: `type;id;name;category;latitude;longitude;website;phone`.
Файл `data/places.csv` специально содержит 5 битых строк, по одной на каждый код ошибки.

## ЛР 2. Своя структура данных и асинхронность

Главное хранилище мест — своё k-d дерево (`KdTree`). ArrayList и другие коллекции java.util в основном коде не используются.

| Файл | Что в нём |
| --- | --- |
| `SimpleArray.java` | свой растущий массив (вместо ArrayList) |
| `KdTree.java` | k-d дерево: вставка, поиск, удаление, поиск в прямоугольнике |
| `SyncKdTree.java` | то же дерево, но методы `synchronized` (защита от гонки потоков) |
| `PlaceGenerator.java` | случайные места в районе Новосибирска |
| `TreePanel.java` | рисунок дерева, пройденные узлы красные |
| `MainFrame.java` | фоновая загрузка и генерация (`SwingWorker`), прогресс, отмена |
| `experiment/Benchmark.java` | замеры: k-d дерево против `TreeMap` |
| `experiment/RaceDemo.java` | гонка потоков и её исправление |

Запуск экспериментов: `./gradlew benchmark` и `./gradlew raceDemo`.

### Сложность операций (n — количество мест)

| Операция | В среднем | Худший случай | Почему |
| --- | --- | --- | --- |
| Вставка | O(log n) | O(n) | спускаемся от корня до листа, глубина дерева ~log n; если места пришли отсортированными, дерево вытягивается в «палку» |
| Поиск по координатам | O(log n) | O(n) | тот же спуск по одной ветке |
| Удаление | O(n log n) | O(n²) | собираем все n мест и вставляем заново все, кроме удаляемого |
| Поиск в прямоугольнике | O(√n + k) | O(n) | ветки, которые не пересекают прямоугольник, пропускаются; k — сколько мест нашли |

### Замеры (мс)

| Операция | n | k-d дерево | TreeMap |
| --- | --- | --- | --- |
| Вставка n мест | 10 000 | 8 | 6 |
| Поиск n мест | 10 000 | 10 | 4 |
| 1000 поисков в прямоугольнике | 10 000 | 7 | 25 |
| 100 удалений | 10 000 | 983 | 0.3 |
| Вставка n мест | 100 000 | 82 | 32 |
| Поиск n мест | 100 000 | 131 | 39 |
| 1000 поисков в прямоугольнике | 100 000 | 11 | 96 |
| 100 удалений | 100 000 | 6392 | 0.2 |

Вывод: по одному ключу TreeMap быстрее, но в прямоугольнике k-d дерево выигрывает в 3–9 раз, потому что отсекает ветки сразу по двум координатам. Удаление у нас медленное, зато его код самый простой.

### Гонка потоков

4 потока по 50 000 вставок в одно дерево:

```
Обычное KdTree     : ожидалось 200000, в дереве 173317, потеряно 26683, исключений 26680
SyncKdTree (защита): ожидалось 200000, в дереве 200000, потеряно 0, исключений 0
```

## ЛР 3. Сериализация и тесты

Места можно сохранить в файл и загрузить обратно в двух форматах: бинарном и JSON (кнопки «Экспорт» и «Импорт»). Оба формата реализуют общий интерфейс `Serializer`, поэтому окно и тесты не знают, какой формат внутри.

| Файл | Что в нём |
| --- | --- |
| `Serializer.java` | общий интерфейс: `save`, `load`, номер версии формата |
| `PlaceData.java` | место в виде простых полей — то, что лежит в файле; проверка данных при чтении |
| `BinarySerializer.java` | бинарный формат через `DataOutputStream` / `DataInputStream` |
| `JsonSerializer.java` | JSON через библиотеку Jackson |
| `FormatException.java` | своё исключение для битых файлов (коды `BROKEN_FILE`, `UNSUPPORTED_VERSION` и др.) |
| `experiment/FormatBenchmark.java` | сравнение форматов: размер и время |
| `src/test/java/poi/SerializerTest.java` | 11 тестов JUnit 5: 5 положительных и 6 отрицательных |

В каждом файле записана версия формата (`VERSION = 1`). Если версия другая или файл обрезан, испорчен, чужой — программа не падает, а показывает ошибку с кодом, и данные в таблице не меняются.

Примеры в `data/`: `novosibirsk.json`, `novosibirsk.bin` (целые), `broken.json`, `broken.bin` (обрезаны).

Запуск тестов: `./gradlew test`. Сравнение форматов: `./gradlew formatBenchmark`.

### Сравнение форматов (10 000 мест, среднее из 5 запусков)

| Формат | Размер, КБ | Запись, мс | Чтение, мс |
| --- | --- | --- | --- |
| Бинарный | 566 | 16 | 8 |
| JSON | 2118 | 16 | 25 |

Вывод: бинарный файл в 3,7 раза меньше и читается в 3 раза быстрее, потому что числа хранятся готовыми байтами (double — всегда 8 байт), а не текстом с именами полей. Зато JSON человек может открыть и прочитать в блокноте, и его понимают другие программы. JSON записан с отступами, без них он был бы меньше.

## ЛР 4. Версии формата и миграции

У места появились два новых поля, и из-за этого формат файла получил новые версии:

| Версия | Что в ней | Значение для старых файлов |
| --- | --- | --- |
| 1 | как в ЛР 3 | — |
| 2 | + рейтинг (число от 0 до 5) | 0.0 |
| 3 (текущая) | + заметка (текст) | пустая строка |

Версия записана в каждом файле: в JSON — поле `schema_version` (в файлах ЛР 3 оно называлось `version`, программа понимает оба имени), в бинарном файле — число сразу после подписи `MAGIC`.

**Миграция** — перевод старых данных в новую версию при чтении. Она идёт шагами: файл версии 1 проходит шаги 1 → 2 → 3, файл версии 2 — только 2 → 3.

| Файл | Что в нём |
| --- | --- |
| `Migration.java` | интерфейс одного шага миграции |
| `MigrationV1toV2.java` | шаг 1 → 2: рейтинг по умолчанию 0.0 |
| `MigrationV2toV3.java` | шаг 2 → 3: заметка по умолчанию, проверка рейтинга |
| `Migrator.java` | применяет шаги по цепочке, проверяет версию, убирает поля при сохранении в старую версию |
| `src/test/java/poi/MigrationTest.java` | 13 тестов миграций: 7 положительных и 6 отрицательных |
| `src/test/resources/migration/` | файлы-образцы версий 1 и 2 для тестов |

Что умеет программа:

- **Импорт старого файла.** Окно спрашивает «Файл версии 1. Мигрировать до 3?». Если ответить «Нет», таблица не меняется.
- **Экспорт в любую версию.** При экспорте выбирается версия 3, 2 или 1. Для старой версии окно предупреждает, какие поля потеряются. Файл версии 1 устроен точно как в ЛР 3, поэтому его открывает и программа из ЛР 3.
- **Ошибки при миграции.** Файл более новой версии — код `VERSION_TOO_NEW`. Неправильный рейтинг в файле версии 2 — `MIGRATION_FAILED`. Обрезанный или чужой файл — `BROKEN_FILE`. Во всех случаях программа не падает, а данные в таблице не меняются.

Формат CSV из ЛР 1 не менялся: у мест из CSV рейтинг 0.0 и пустая заметка.

Примеры в `data/`: `novosibirsk.json`, `novosibirsk.bin` (версия 1, из ЛР 3 — на них видно вопрос о миграции), `novosibirsk-v3.json`, `novosibirsk-v3.bin` (версия 3, с рейтингом), `future.json` (версия 9 — «из будущего»).

Запуск тестов: `./gradlew test` (всего 24 теста).
